# Design decisions

For each decision: what was chosen, the alternatives considered, and why. The selection criteria were the Theme 4 constraints ("simple and cheap beats a heavy agent orchestration stack"), CPU-only reproducibility, and being explainable to a jury.

| # | Decision | Alternatives | Why |
|---|---|---|---|
| D1 | **Section-level chunks** (split only above 160 words) | Fixed 256-token windows | A section is the natural citation unit (`[DOC §S]`), and corpus sections are 40–120 words. Fixed windows would cut sections and blur citations. |
| D2 | **MiniLM-L6 embeddings via plain `transformers`** | sentence-transformers, bge-small, e5 | Already cached, 22M parameters, runs on CPU. Mean pooling reproduces sentence-transformers exactly without the extra dependency. |
| D3 | **Exact numpy dense search, no FAISS** | FAISS flat/IVF | At 57 chunks (or a few thousand) an exact matrix product takes under 1 ms, has no recall loss and needs no native build. `CorpusIndex._dense` is the single swap point. |
| D4 | **In-house BM25 (~40 lines)** | rank-bm25 | Inspectable scores, no dependency, identical tokenisation to the controller. |
| D5 | **Reciprocal rank fusion (k = 60)** | Weighted score sum | Rank-based, so there is no score calibration between cosine and BM25. It's the standard reference method and easy to explain. |
| D6 | **ms-marco-MiniLM-L6 cross-encoder reranker** | No reranker; bge-reranker-base | About 5 ms per pair on CPU. It fixes the main precision failure (dense retrieval confusing "Pune office rooms" with "Pune venues"). It's modular, and the ablation disables it. |
| D7 | **Learned controller = two logistic regressions + guardrails** | LLM call per chunk; pure rules | An LLM per chunk would add hundreds of ms and cost to every chunk, which is exactly what the guide warns against. Pure rules can't tell refinements from new requests; the ablation shows 0% refinement detection for rules. LR trains in under 1 s and its weights are readable. |
| D8 | **Deterministic decomposition (segment → re-attach → retrieval-overlap merge → entity carry-over)** | LLM decomposition | Zero cost, under 5 ms, and it can't invent sub-questions. The merge step uses the corpus as the judge of "same intent". Limitation: it relies on surface coordination (see limitations). |
| D9 | **Extractive synthesis by default; LLM optional behind an interface** | Always-on LLM | No API key is available in the build environment, and extractive answers make every benchmark number reproducible and $0 per turn. They also can't inject outside knowledge. The optional LLM path is validated by the same grounding checker. |
| D10 | **Abstention gate = logistic regression over (cross-encoder logit, answer-coverage, cosine), calibrated per corpus** | Single logit threshold (v1); hand-shaped threshold grid | A single cross-encoder threshold let topical-but-unanswerable questions through ("CEO of Veltrix"). Coverage adds the missing "is the asked-about concept even in the evidence" signal. An LR is the simplest principled combiner and reports leave-one-out accuracy rather than in-sample accuracy. It is fitted on the pipeline's own sub-query form (decomposer focus), because the cross-encoder scores fragments differently from full questions. |
| D11 | **Facet filter derived from titles** | Hard-coded city list; metadata schema | Generic, with no domain constants. It only activates for document families it discovers. |
| D12 | **Provisional-retrieval cache keyed by content-stem set** | Embedding similarity threshold | Exact and explainable: a sub-query is reused only if it asks for exactly the same content words. |
| D13 | **SSE over `StreamingResponse`** | WebSockets, sse-starlette | Turn traffic is one-way (server → client) once the chunks are posted. It needs no extra dependency and works through `fetch()`. |
| D14 | **Vanilla HTML/JS dashboard served by FastAPI** | React/Next.js | No Node build step, one process and one port. The evaluation weight is on behaviour, not UI polish. |
| D15 | **Simulated transcript streams at 150 wpm plus 0.5 s end-pointing** | Live ASR | The guide allows simulated voice input. The same timing rule is used for the benchmark and custom UI input. |
| D16 | **Synthetic development corpus** | — | No corpus was present in the repository. The corpus is clearly marked `synthetic: true` and mirrors the guide's scenarios (Pune workshop, cancellation, catering, travel reimbursement). Dropping the official corpus into `data/raw/` and re-running `build_index.py` is all that ingestion needs; the benchmark gold labels would have to be re-authored. |
| D17 | **Evaluation split into controller-dev / calibration / retrieval-eval / dev streams / held-out** | One benchmark | The first benchmark was used to find and fix failures, so it can no longer be called held-out. A new held-out set was written and frozen (hash plus overlap test) before the fixes. |
| D18 | **Speculative synthesis prep during speech** | Score sentences only after utterance end | Sentence scoring by the cross-encoder was the largest post-utterance cost. Doing it when the provisional retrieval completes moves it off the critical path whenever the evidence does not change. |
| D19 | **Imperative-on-previous-answer and new-topic-content features in the intent classifier** | Keyword rules; more training data only | They are generic linguistic cues (imperative verb plus "that/it" vs a declarative statement adding new corpus terms), and the LR learns their weights. No utterance-specific rule was added. |
| D20 | **Leading-context merge and focus span in the decomposer** | Treat every clause as an intent | Rambling speech ("so yesterday I was chatting with my manager… so how often do laptops get replaced?") otherwise produced context-only sub-queries and a diluted answer focus. |
| D21 | **Format-agnostic loader that keeps source section ids** | Markdown-only (v1) | The official corpus format is unknown. Keeping source numbering ("4.2", "p3") makes citations match the source documents. |
| D22 | **Known failures as strict expected-failure tests** | Delete or hide them | They stay visible in CI and flag loudly if behaviour changes. |
| D23 | **Abstention gate refitted on development + calibration data (116 examples); feature set chosen by leave-one-group-out** | Keep the 56-query gate; tune on held-out | The first held-out run showed over-abstention. The fix could only use development data: dev-set sub-queries labelled from gold sections, and groups (all sub-queries of one utterance) kept together in cross-validation. The 6-feature aggregate model was *not* selected, because its leave-one-group-out accuracy was lower than the 3-feature model's once labels were corrected. |
| D24 | **Weak-evidence ("hedged") answer band, enabled only if pre-set criteria hold** | Always hedge; never hedge | Hedging would raise coverage, but only if hedged answers are mostly answerable. The criteria (≥ 75% answerable in the band; ≤ 10% of unanswerable examples admitted) were fixed before looking. No band met them, so none is active. The mechanism stays in the code, off by default. |
| D25 | **TTFT counts the first output of any kind (a claim or the abstention message)** | First claim only | Measuring only to the first claim silently dropped abstaining turns from latency statistics, which favours a system that abstains more. A per-turn *utterance-end lag* (actual vs scheduled) is also recorded as a CPU-contention check. |
| D26 | **Quantity constraints ("for 30 people") checked against the evidence** (`retrieval/constraints.py`) | Leave ranking to the cross-encoder; add a capacity-specific rule; tune on examples | Neither the cross-encoder nor BM25 compares numbers. In the guide's own Example 1, the venue sections that fit 30 people ranked 4th and below, so sub-query 1 answered with "plan a workshop" text. A "for [about] N ⟨noun⟩" phrase is now read as a minimum. If none of a sub-query's top 3 chunks states ≥ N of that noun, up to 2 chunks that do are moved in behind the reranker's top result, and matching sentences are selected first. It is linguistic, not corpus-specific. The phrase pattern was fixed from the guide and the development set (the only phrasing there was "for 30 people") *before* the held-out re-run, and was not widened afterwards. It is on for the proposed system only; the baseline is unchanged, and `ablation_no_quantity_constraints` measures it. |
| D27 | **Guide-shaped output record per turn** (`TURN_SUMMARY.output_record`) | Keep the information spread over events only | The guide (§4) specifies a structured record with `retrieval_events` (`timestamp_s`, `query`, `trigger`), `sub_queries`, `answer`, `citations` as `Doc §Section`, `uncertainty`, and for suppression `retrieval_required: false` plus a `reason`. The record is derived from the event log, so it cannot disagree with the telemetry. |
